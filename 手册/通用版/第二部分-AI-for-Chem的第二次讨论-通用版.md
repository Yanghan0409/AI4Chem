## 引言

开始学习 AI 之前，值得先问一个更基础的问题：**计算机到底是什么？**

为什么同一台机器既能处理光谱，又能运行分子计算？
为什么有的任务适合 GPU，有的仍需要 CPU？
为什么一段代码在自己的电脑上运行正常，换台机器却报错？
这些问题背后，涉及硬件怎样执行操作、软件怎样组织任务，以及人与机器怎样表达和传递要求。

本章沿原来的五问展开：

1. **发展历史**：从巴贝奇与洛芙莱斯，到图灵、香农、冯·诺伊曼、霍珀、汤普森与里奇，计算机的哪些关键问题逐步得到解决？
2. **硬件**：计算机需要哪些基本功能，CPU、GPU 等处理器怎样分工？
3. **编程语言**：自然语言与机器执行之间隔着什么，为什么需要不同编程语言？
4. **操作系统**：谁来管理程序和硬件，运行环境为什么影响代码能否工作？
5. **本质**：可编程机器与普通工具有什么区别，“处理”与“理解”又怎样区分？

历史帮助理解为什么会有这些组成，硬件与软件说明它怎样工作，最后再回到它能够承担什么样的化学研究任务。
数据怎样表示、怎样整理，以及机器学习怎样训练，留到后面的章节展开。

## 2.1 发展历史：通用机器怎样逐步形成

### 2.1.1 从重复算数到可编程的构想

早期计算工具的重要目标，是减少重复计算中的劳动与错误。
巴贝奇设计的差分机面向数表计算；后来构想的分析机，则把目标推进到可以按不同指令完成不同计算的机器。

分析机设计中已有用于保存数值的部分、执行运算的部分，以及通过穿孔卡片控制操作的安排。
它在当时没有完整建成，但展示了一个重要转变：**机器的任务可以由一套可更换的操作步骤决定。** [巴贝奇机器设计资料](https://www.computerhistory.org/babbage/engines/)

1843 年，阿达·洛芙莱斯在介绍分析机的注释中，给出了计算伯努利数的步骤，也讨论了机器处理数字以外符号的可能性。
她常被称为早期编程先驱；对本章更重要的是，这种认识把机器的用途从“算一个数”扩展到了“按规则处理可以表示的对象”。[洛芙莱斯与分析机资料](https://www.computerhistory.org/babbage/adalovelace/)

### 2.1.2 图灵把“什么能够计算”变成数学问题

要设计一台通用机器，首先需要说明：什么叫按规则计算？哪些问题能由这样的步骤解决？

图灵在 1936 年的工作中，用读写符号、改变内部状态和移动读写位置的抽象机器，研究了这些问题。
常见的图灵机示意图中有纸带和读写头，它是帮助讨论计算的数学模型，不是要求真实电脑装一条无限长纸带。

**通用机器的意义是，一套机器可以在给定另一套机器的描述后，模拟其计算过程。**
这为“同一台机器换程序做不同工作”提供了理论基础，也揭示并非所有形式化问题都存在通用求解程序。[图灵原始论文](https://www.cs.virginia.edu/~robins/Turing_Paper_1936.pdf)

这里还要区分两种困难：有的任务原则上可计算，但现实所需时间或存储太多；有的则在理论上没有解决所有情形的算法。
“通用”不等于任何问题都能在有限资源下轻松解决。

### 2.1.3 香农与存储程序结构连接逻辑和机器

香农在 1937 年的研究中，把布尔逻辑用于继电器与开关电路分析。
布尔逻辑处理真假等关系，而开关电路有可以区分和控制的状态，两者可以建立对应。
这样，逻辑关系就能够通过电路实现，不再只是写在纸上的符号。[香农原始研究](https://dspace.mit.edu/entities/publication/2dffdeb7-2862-4575-8a8e-b29fb59319e5)

香农后来建立的信息论，又为消息、编码与通信提供了定量框架。
这与“让开关实现逻辑”有关联，但属于不同工作，不能混成一次发明。

接下来一个重要工程问题是：机器怎样保存并自动执行一连串指令？
1945 年冯·诺伊曼署名的 EDVAC 报告系统描述了相关设计，把指令和数据存入存储器，交由运算与控制部分组织执行。
这是多人共同推动的成果，不能理解成一人独自发明现代计算机。[EDVAC 报告原件](https://archive.computerhistory.org/resources/text/Knuth_Don_X4100/PDF_index/k-8-pdf/k-8-u2593-Draft-EDVAC.pdf)

**程序也能被保存、读取和更换，使改变计算任务不必总靠重新接线或改造机器。**
这正是后面理解软件的起点。

### 2.1.4 编程与软件系统让更多人使用机器

硬件能够执行指令，还不等于人容易编写这些指令。
霍珀与合作者开发早期编译系统 A-0，并推动更接近人的表达方式以及 COBOL 的发展，帮助减轻编程负担。
早期编译系统与今天的实现并不完全相同，但它们共同推动了“让软件帮助生成和组织机器操作”的方向。[A-0 档案](https://americanhistory.si.edu/pt/collections/archival-item/sova-nmah-ac-0324-ref1044)

汤普森与里奇等人在贝尔实验室发展 Unix，里奇创造 C 语言；用 C 重写 Unix 的重要部分，使系统更容易在不同机器间发展和移植。
这并没有消除硬件差异，但减少了软件只能围绕某一台机器编写的限制。[里奇对 C 语言发展的回顾](https://www.bell-labs.com/usr/dmr/www/chist.html)

| 线索 | 帮助回答什么问题 |
|---|---|
| 巴贝奇与洛芙莱斯的构想 | 机器能否按可更换的步骤处理不同任务？ |
| 图灵的理论 | 什么是可计算，通用机器意味着什么？ |
| 香农的电路工作 | 逻辑怎样落实到可控制的物理状态？ |
| 存储程序结构 | 指令与数据怎样保存并自动执行？ |
| 霍珀等人的编程工作 | 怎样让人更容易表达机器要做的事情？ |
| Unix 与 C 的发展 | 怎样让复杂软件协同工作，并减少移植负担？ |

此后的电子器件、晶体管、集成电路与微处理器，让机器更小、更可靠，也逐步进入个人电脑、网络与大规模计算的场景。
这是一项连续的集体工程；认识历史的目的，是看清问题怎样被逐步解决，而不是把计算机史背成一张人物发明表。

## 2.2 硬件：机器靠什么执行任务

### 2.2.1 先认识功能，再对应实际部件

从常见的存储程序结构出发，可以把基本功能分成运算、控制、存储、输入和输出。

| 功能 | 主要做什么 | 常见部件或例子 |
|---|---|---|
| 运算 | 进行加减、比较等操作 | CPU 中的运算部分 |
| 控制 | 组织取指令、执行及后续步骤 | CPU 中的控制部分 |
| 存储 | 保存指令、正在处理的数据与结果 | 内存，以及硬盘、SSD 等长期存储 |
| 输入 | 接收外部信息 | 键盘、仪器接口、网卡 |
| 输出 | 传出结果或控制信号 | 显示器、打印机、网卡或控制接口 |

这里是功能划分，不等于每项都必须对应一块独立硬件。
网络接口既能输入，也能输出；服务器可以不接显示器，一些设备也不需要独立硬盘或显卡。

在常见电脑中，**内存用于暂存正在运行的程序和数据，硬盘或 SSD 用于长期保存文件**。
普通 RAM 通常在断电后失去内容，因此“内存大”与“硬盘空间大”解决的不是同一个问题。

主板和连接电路负责把部件连起来，电源提供能量；固件则保存启动等底层工作所需的程序。
固件是程序，不宜与承载它的芯片完全混为一类。

### 2.2.2 0 和 1 怎样对应到电路

0 和 1 是用于表示信息的符号，电路需要用实际可区分的状态承载它们。
在常见数字电路中，可以用不同电压范围表示逻辑状态，再由电路组合完成判断与运算。

晶体管可以先理解为受电信号控制的开关元件：一个位置的信号变化，影响另一路的导通情况。
许多晶体管按照设计连接起来，便可以组成执行逻辑、保存状态和组织计算的电路。

**不是先有一个抽象的“1”变成电流，而是人规定哪些物理状态代表 0 或 1，再设计能够处理这些状态的电路。**
“开或关”是入门类比，实际元件和电压的行为比理想开关复杂，不需要在本章展开全部半导体物理。

1947 年，哈佛 Mark II 团队曾把继电器里发现的飞蛾贴进日志，留下关于实际“bug”的记录。
它说明故障可以来自物理部件，但不是“bug”这个工程用语的起源，也不宜直接归为霍珀一人亲自发现。[飞蛾日志馆藏](https://americanhistory.si.edu/collections/object/nmah_334663)

### 2.2.3 CPU 与 GPU 的区别在于任务怎样组织

**CPU 是中央处理器，GPU 是图形处理器；二者设计侧重点不同，常在同一系统中配合。**

| 比较角度 | CPU | GPU |
|---|---|---|
| 主要侧重 | 复杂流程、分支判断与较快的单任务响应 | 对大量数据执行相似操作，完成较大的总计算量 |
| 任务特点 | 步骤之间依赖较多，需要灵活决定接下来做什么 | 许多计算可以分配给不同单元同时进行 |
| 常见分工 | 组织程序、处理数据、安排任务 | 图形处理与适合并行的计算加速 |

“几位博士与许多小学生”的比喻，想说明少量强通用核心与大量计算单元的分工，但容易让人误以为这是聪明程度的比较。
更准确的判断是：**这项工作能不能拆开，同时做许多相似计算？**

例如，图形处理中，要根据顶点等信息计算画面的许多部分；许多相近操作可以批量组织，适合 GPU。
若每一步必须等前一步决定下一步，增加计算单元也不能自动把这一串依赖消掉。

CPU 也能并行计算，GPU 也能处理条件分支。
只是不同分支与依赖可能降低 GPU 的执行效率，不能说 GPU 遇到判断就完全不会跳转，或必须把所有可能分支全部算完。[CUDA 并行计算说明](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/programming-model.html)

### 2.2.4 为什么 AI 训练经常使用 GPU

许多神经网络训练需要反复进行大量乘法和加法，把许多数值按相同形式组合起来。
这些操作常组织为矩阵计算；这里可以先把矩阵理解成按行列排列的数值，不必先学完线性代数。

其中许多操作能够拆开并行，适合 GPU 的设计。
但整个训练不是所有步骤都彼此独立，还涉及数据传输、顺序依赖和任务组织，CPU 仍然承担重要工作。

**GPU 的优势来自任务与硬件结构相匹配，不代表所有 AI 或化学计算都必须使用 GPU。**
程序是否支持加速、数据量、显存容量和计算方式，都会影响实际效果。

NPU 是另一类侧重神经网络计算的处理器，通常为特定计算和部署需求设计。
它体现了进一步专用化的方向，但能否更省电、更快或更小，要在具体任务与设备条件下比较，不能单凭名称判断。

### 2.2.5 算力数字怎样理解

“算力”不是只指 GPU，也不只有一种指标。
常见的 FLOPS 表示每秒浮点运算次数，TFLOPS 表示每秒万亿次浮点运算；TOPS 则表示每秒万亿次指定操作，阅读时要看采用什么运算和计数方法。

所谓理论峰值，是按计算单元数量、频率和每周期能够执行多少操作等条件估计的上限，不是任何程序都能达到的速度。
同一硬件在不同数值格式下，峰值也可能不同，例如 FP32 指一种 32 位浮点格式。

**比较算力，应同时说明运算类型、数值格式和测试条件。**
更高的峰值不保证实际任务更快：数据搬运、显存容量、带宽、软件实现和任务能否并行都可能成为限制。
带宽可以先理解为一定时间内能传递多少数据，计算单元再多也需要及时取得数据。

因此，资料中的理论计算公式适合帮助理解指标来源，不应当作适用于所有芯片和所有任务的通用性能公式。
具体设备的配置与数值会变化，选型时应再核对相应官方规格与任务测试。

### 2.2.6 计算的载体不只一种

从“电压状态代表符号”还可以追问：是否能用其他物理过程承载和操作信息？
光通信、光计算以及利用分子过程处理信息的探索，都提示计算与信息处理不必局限于同一类器件。

但传输信息与完成计算是不同功能。
有光信号，不等于已经有一台能够存储、执行任意程序并稳定读出结果的通用机器。

要评价一种载体，还要看状态能否可靠控制、操作怎样组合、结果怎样读取，以及与其他部件怎样连接。
器件尺寸、制造、误差与能量开销都需结合具体方案分析，不能仅凭“光传播快”断言处理器就一定更快或不发热。

## 2.3 编程语言：怎样把要求变成可执行操作

### 2.3.1 自然语言可以是入口，但要求仍要明确

“为什么不能直接用自然语言告诉计算机”，更准确地说，是自然语言的要求怎样被落实成操作。
今天可以通过语言与软件交互，但硬件仍需执行明确规定的指令，不能仅凭一句模糊要求确定全部处理细节。

“把这组光谱处理一下”就包含许多没有说明的选择：

- 使用哪段波长范围？
- 怎样扣除背景？
- 是否归一化，按什么规则？
- 输出图像、峰位还是一张数值表？

这些要求即使交给 AI，也需要说明和检查。
**编程语言的作用之一，是把操作、条件和数据关系表达得更明确、可执行和可复查。**

AI 可以生成代码，也可以选择已有工具或返回文字，不是每次回答都必然经历“生成代码再执行”的过程。
无论采用哪条路径，都要检查实际执行的操作是否符合研究意图。

### 2.3.2 从机器指令到高级语言

处理器有自己能够执行的操作，以及相应的指令编码规则，这称为指令集。
汇编语言给机器指令提供人更容易辨认的名称；高级语言则让人以变量、条件、循环和函数等形式组织工作。

这里可以先把“函数”理解为能够反复调用的一段明确操作。
例如，把读取一组光谱并扣背景写成可调用的步骤，便不必每处理一份文件都重新描述底层操作。

编译器、解释器和相关运行软件，负责按照语言规则使程序最终在机器上执行。
不同语言的实现路径不完全相同，也不必都先生成一份可见的汇编文件。

**越靠近使用者的一层，可以让人少操心一部分底层细节，但底层的限制并没有消失。**
这也是为什么能写出一段看起来正确的代码，还需要实际运行并检查结果。

### 2.3.3 不同语言面对不同取舍

| 语言或类别 | 常见用途 | 为什么会采用它 |
|---|---|---|
| Python | 数据整理、科学分析与 AI 工作流程 | 表达较方便，相关工具和程序库丰富 |
| C/C++ | 底层软件与高性能计算部分 | 对资源和执行方式有较多控制能力 |
| JavaScript | 网页交互及相关应用 | 能与网页运行环境配合 |
| SQL | 查询和整理数据库中的记录 | 便于表达按条件筛选、关联与汇总 |

这些是典型用途，不是排他的边界。
Python 程序也常调用由其他语言实现的高效计算部分；一项研究工具可以由多种语言协作构成。

语言的取舍还涉及可读性、安全性、已有软件和维护成本。
认识这种分工，比先把所有语言名称列全，或判断哪一种最先进，更有助于开始工作。

## 2.4 操作系统：谁来管理硬件与程序

### 2.4.1 操作系统提供共同的管理层

操作系统可以比作“管家”：统一管理资源，并让应用程序通过共同的方式使用文件、设备和其他功能。
例如，程序要求读取一个文件，不必为每一种硬盘重新设计底层通信过程。

| 主要工作 | 解决什么问题 |
|---|---|
| 管理处理器与内存 | 组织多个任务，分配资源，减少相互干扰 |
| 管理文件、设备与网络 | 提供共同的访问方式，并通过驱动等软件连接硬件 |
| 管理权限与交互 | 区分哪些操作被允许，支持命令行或图形界面使用 |

这里的驱动，是帮助系统与特定设备交互的软件。
共同接口也不代表所有错误都能隔离，操作系统和驱动本身仍可能出问题。

简单嵌入式程序可以不使用完整操作系统。
但在运行多种应用、连接多类设备的常见电脑上，这种共同管理层大幅减轻了软件开发与使用负担。

### 2.4.2 Windows 与 Linux 不只是界面不同

| 比较角度 | Windows | Linux 及其常见发行版 |
|---|---|---|
| 组织与许可 | 微软主导的专有系统 | Linux 内核开源，完整系统通常由内核及配套软件组成 |
| 常见科研场景 | 桌面办公、商业软件与仪器控制 | 服务器、共享计算、自动化与定制部署 |
| 使用方式 | 广泛使用图形界面，也支持命令行与脚本 | 服务器常用命令行，也有完整图形桌面 |
| 软件与维护 | 常通过安装包、商店或组织部署管理 | 常通过发行版的软件仓库与包管理工具维护 |

严格说，Linux 是内核；Ubuntu 等发行版把内核与各种配套软件组织成可使用的系统。
Linus Torvalds 与网络协作者发展的内核，以及 GNU 等项目的软件，共同参与了这一生态，并非某个人从头独自写完全部系统。[Linux 内核说明](https://docs.kernel.org/admin-guide/README.html)

“一切皆文件”是一种理解 Unix 类系统接口的概括：许多资源可以通过类似文件的方式访问。
它不是说所有硬件在物理上就是文件，也不是插入 U 盘后其全部内容只变成一个普通文件。

实际选择还要看软件支持和实验条件。
不能把 Windows 等同于只能点鼠标，也不能把 Linux 等同于只有命令行、所有软件都免费，或只有专家才能使用。

### 2.4.3 代码运行依赖环境

同一段源代码在另一台电脑上出问题，常见原因不只一种。

| 环境差异 | 可能出现什么 | 复现时记录什么 |
|---|---|---|
| 操作系统及系统接口 | 可执行文件不能直接运行，某些功能不可用 | 系统名称、版本与所用软件支持范围 |
| 处理器类型 | 面向一种机器指令编译的程序，另一种不能直接执行 | CPU 架构及是否需要重新编译或其他支持 |
| 语言与程序库 | 缺少功能，或相同调用出现不同表现 | 语言版本、依赖库与版本 |
| 驱动与计算硬件 | 无法使用 GPU 或特定设备 | 硬件型号、驱动和相关计算软件版本 |
| 文件与使用权限 | 找不到文件、打不开文件或读出乱码 | 路径、权限、编码及输入文件 |

源代码与已经编译好的程序也需要区分：前者可能通过调整后重新运行，后者往往与具体平台有更直接的联系。
把文件搬过去，不一定把它依赖的环境一起搬过去。

1996 年 Ariane 5 首飞事故说明了另一层环境问题：沿用的模块包含不适合新飞行条件的假设，一次数值转换超出目标整数范围，相关异常又造成系统停止工作。
主备系统使用相同软件，并没有避开这种共同失效。[事故调查报告](https://www-users.cse.umn.edu/~arnold/disasters/ariane5rep.html)

它不是普通软件安装失败的同一种故障，但共同提醒我们：**复用代码，需要重新检查输入范围、运行条件与错误处理。**
对科研复现，应同时保存代码、数据和环境说明，而不是只保存一份最后结果。

### 2.4.4 学习 AI 不必先更换整套系统

如果现有工具支持 Windows，可以先在已有环境中学习。
需要 Linux 软件时，可以根据条件使用 WSL、独立 Linux 系统或远程服务器。

WSL 是在 Windows 中使用 Linux 环境的一种方式；其中 WSL 2 使用真实 Linux 内核与轻量虚拟机，不能把所有 WSL 版本都概括为同一种虚拟机方案。[WSL 官方说明](https://learn.microsoft.com/en-us/windows/wsl/compare-versions)

远程连接则是在另一台机器上运行任务，本地电脑负责交互。
服务器是否适合，还要看任务、权限、软件支持与实际资源，而不是只看租用价格。

虚拟环境可以隔离部分软件依赖，容器可以打包一部分运行环境，但都不能消除所有系统、硬件和驱动限制。
本章先认识这些方法的用途，具体安装与配置按后续任务展开。

## 2.5 本质：通用性、处理与理解

### 2.5.1 可编程性让同一机器承担不同任务

与许多功能较固定的工具相比，通用计算机的重要特点是：**通过更换程序，同一套硬件可以自动完成不同的信息处理任务。**

运行绘图软件、处理光谱、进行分子计算，并不需要每次重新制造一台机器。
程序还可以依据中间结果作条件判断、重复操作，连续执行许多步骤。

“制造工具的工具”是一个有帮助的比喻：在既有硬件和软件之上，可以继续开发新的研究工具。
但“通用”仍受算法、时间、存储和实际输入限制，不能解释为计算机在现实中无所不能。

### 2.5.2 程序也可以成为处理对象

计算机不仅处理实验数值，也可以处理程序本身。
编译器处理代码，编辑器帮助修改代码，程序还可以产生供后续执行的新指令或配置。

这保留了一个重要观察：功能并不完全固定在机器外形中，可以通过软件继续改变。
但能修改程序，不自动意味着系统具有自主意图；是否修改、怎样修改，以及修改后是否有效，仍取决于具体过程与检查。

另一个特点是**层级抽象**：底层提供相对明确的操作和接口，上层可以组合出更复杂的功能。
这里的“抽象”，可以先理解为把许多细节封装起来，让使用者围绕更高层的任务工作。

从电路到机器指令、编程语言，再到软件界面，不同层次可以协作。
层次越高，通常越方便表达任务，但不是可以无视底层条件任意发挥。

### 2.5.3 “处理”是机制，“理解”涉及评价标准

计算机执行运算、变换符号和处理输入，是可以描述和检查的工作机制。
但仅凭这个机制，不能直接结束关于“理解”的争论。

塞尔的“中文房间”思想实验提出：一个不懂中文的人，可以按照规则处理递入的符号，给出从外部看来合适的中文回答。
他的论证强调，形式规则的执行本身不足以证明理解了意义。[塞尔原始论文](https://www.cambridge.org/core/journals/behavioral-and-brain-sciences/article/abs/minds-brains-and-programs/DC644B47A4299C637C89772FACC2706A)

这是一种重要观点，不是已经解决全部争议的实验结论。
另一种评价思路更关注系统整体的能力：它能否在变化条件下完成任务、利用上下文、修正错误，并把已有能力用于新问题？

**具有人的主观体验，与在某类任务上表现出可用能力，是不同判断。**
语言表现好，不能单独证明意识；基于计算实现，也不能单独证明它不可能获得任何可称为理解的功能。

香农曾通过预测后续字母等办法研究英文的冗余与可预测性。
它有助于说明上下文包含统计规律，但不能由“能预测”直接推出已经理解，也不能推出只能机械复述。[香农 1951 年论文](https://doi.org/10.1002/j.1538-7305.1951.tb01366.x)

对于 AI 中超出预期的任务表现，也需要结合测试条件与评价方法分析。
不能仅凭几个生动例子，就把“完整重构世界”或“只会重复”写成已经证实的统一结论。

### 2.5.4 “理解化学”要落到具体能力与证据

这项判断至少可以拆成几个问题：能否正确表示结构，能否使用相关知识，能否预测未见过的对象，能否给出与实验一致的解释？
这些能力不能仅凭一段流畅回答一起得到确认。

例如，AI 给出的反应优化建议可能过于宽泛，甚至采用与现有条件不相称的方案。
这可能反映上下文不足、任务约束不清或模型能力不足；一次使用经历不能代表所有系统，也不能仅凭补充数据库就保证解决。

同样，能够输出结构或机理图，不等于证明候选能够合成、结构真实存在，或机理成立。
**表示化学、作出预测、解释机制与完成实验验证，需要分别检查。**

| 希望系统做到什么 | 可以怎样评价 |
|---|---|
| 正确处理结构 | 核对连接、立体信息、化合物身份与输入输出 |
| 提出可用建议 | 检查是否符合任务条件、来源与现实限制 |
| 预测性质或结果 | 在未用于建立关系的对象上比较预测与测量 |
| 支持机制解释 | 检查论证与独立实验证据是否相符 |

因此，科研使用中与其只问它“懂不懂”，更需要问它具体完成了什么、依据是什么、在哪些条件下可靠。
这个标准与第一章对科学判断的要求相连，也为下一章的数据问题留下入口。

### 2.5.5 AI 与量化计算不是“猜测”和“真解”的简单对立

Gaussian 等软件提供量子化学计算方法；分子动力学则根据选定的模型描述体系运动。
它们都有理论、输入、近似和适用条件，并不是没有误差的现实复制。

以密度泛函理论 DFT 为例，它以电子密度等理论关系为基础处理电子结构问题，实际计算仍采用具体近似。
不能把它概括成“从氢原子方程直接硬解所有分子”。[DFT 奠基论文](https://journals.aps.org/pr/abstract/10.1103/PhysRev.136.B864)

机器学习通常利用数据建立预测关系，也可以结合物理知识。
它不只是统计某个答案出现多少次，更不应简单类比成看选项长短猜答案；其可靠性需要通过相应数据与验证检查。

两类方法可以配合，例如利用学习方法加速或辅助物理计算，再用实验和理论约束检查结果。
本章先区分它们建立关系的主要依据，不展开具体算法。

### 2.5.6 自动化与新认识是两个观察角度

把计算工具与实验设备连接，可以帮助自动安排或执行部分实验，但其中还有样品处理、控制、异常识别与验证等工程问题。
自动执行更多步骤，并不自动意味着已经理解实验。

还可以进一步追问：工具只是让已有工作做得更多、更快，还是帮助获得过去难以观察的数据、提出过去难以检验的问题？
扩大规模与改变观察方式，都可能对研究有价值，不能只用其中一种衡量全部进展。

随着化学与材料记录积累，数据驱动的方法可能承担更多工作。
这种方向能推进到什么程度，取决于数据、表示、测量与验证条件；它是值得研究的问题，不是本章能够宣布的学科发展定论。

## 2.6 本章小结

1. **历史围绕问题逐步发展。** 可编程构想、可计算理论、逻辑电路、存储程序、编程工具与操作系统，共同形成了今天使用通用机器的基础。
2. **硬件功能需要协同。** 运算、控制、存储、输入和输出是基本分工；物理状态承载符号，软件组织这些能力完成任务。
3. **CPU、GPU 与专用处理器各有侧重。** 是否能并行、数据搬运和程序支持，影响实际性能；算力数字需说明口径，不能直接代替任务测试。
4. **编程与操作系统连接要求和执行。** 自然语言可以作为入口，明确的操作与运行环境仍不可缺少；科研复现应保存代码、数据与环境。
5. **通用性不等于无所不能，计算机制也不能独自解决理解之争。** 应区分主观体验、功能能力与科学证据，避免用单一比喻代替判断。
6. **化学应用最终要回到验证。** 结构、预测、建议和机制各有证据要求；数据与物理计算也各有假设和边界，需要具体检查并相互配合。
